# ACRM Session C — Architecture Contract (Draft)

Status: experimental branch; not a release contract.

Session C observes the running ACRM as a continuous system trajectory and prepares governed evolution before a limitation becomes a runtime failure.

## C-A — Neutral observation
C-A records factual observations only. It does not assign severity, score, judgment, cause, topic, promotion status, or intervention.

## Trajectory
Observations are interpreted downstream as a temporally ordered trajectory. Persistence, recurrence, co-occurrence, and change over time belong to accumulated evidence rather than isolated messages.

## Dynamic envelope and tolerance
C-B derives a system-relative operating envelope from trajectory evidence. Tolerance represents approach-to-limit, not a universal fixed error count. A warning region can exist while runtime behavior remains functional; its purpose is early preparation.

A fixed observation count alone is not the architectural trigger for evolution.

## Topic Engine
Topic is inferred in C-B from accumulated observations and temporal/signal profiles. It may determine evaluator relevance but must not modify observations, assert intent, decide promotion, generate code, or mutate runtime.

## C-B — Governed evolution
After sufficient evidence, C-B may formulate and isolate a candidate, test it independently, evaluate it against current context, collect topic-aware reliability/relevance-weighted votes, and produce retain/recommend-switch output for an external controlled handoff.

Passing tests is not promotion. Voting is not execution. A switch recommendation is not runtime mutation.

## Research boundary
This is a target architecture for the experimental branch. It does not claim that autonomous self-modification or empirical self-validation has already been achieved.
